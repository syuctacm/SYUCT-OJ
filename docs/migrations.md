# 数据迁移方案

## 1. 目标

把现有三个域压平成单站点 `system`，同时保留历史题目、提交、比赛和用户统计。

当前生产域及规模（迁移前基线）：

| 域 | 用户关系 | 提交 |
|---|---:|---:|
| `system` | 531 | 41,635 |
| `contest2025` | 62 | 1,303 |
| `select2025` | 113 | 1,291 |

## 2. 迁移原则

- 只在本地 Docker 或测试环境演练。
- 使用本地恢复的脱敏副本。
- 不直接修改生产数据。
- 保留原始 ID 和来源域标记。
- 先 dry-run，再执行。
- 迁移工具必须幂等，可重复运行。
- 每一步都要有数量校验和可回滚方案。

## 3. 迁移步骤

1. 在本地 Docker 启动 MongoDB。
2. 恢复测试数据。
3. 生成迁移前报告：
   - 每个域的用户关系数
   - 文档/题目/比赛数
   - 提交数
   - 榜单统计
4. 迁移 `contest2025` 和 `select2025` 的文档、比赛、训练和作业。
5. 迁移用户关系，合并重复用户。
6. 更新记录的 `domainId` 为 `system`。
7. 写 `legacyDomain` 字段保留来源。
8. 重算题目统计、用户统计和比赛榜单。
9. 生成迁移后报告并对比。
10. 输出失败项、跳过项和冲突项。

## 4. URL 兼容

保留旧 URL 到新 URL 的重定向映射，例如：

```text
/d/system/p/:pid      -> /p/:pid
/d/contest2025/...    -> /...
/d/select2025/...     -> /...
```

重定向规则应集中配置，并有测试覆盖。

## 5. 判题兼容

`hydrojudge` 仍要求任务中包含 `domainId`。迁移后统一使用：

```text
domainId = "system"
```

不得修改判题机来适配新的单站模型。

## 6. 回滚

迁移前保留完整 MongoDB dump。回滚步骤：

1. 停止新后端。
2. 恢复迁移前 MongoDB dump。
3. 恢复旧版本服务。
4. 验证用户、题目、提交、比赛数量。

## 7. 验收

- dry-run 完成且报告可读
- 迁移前后数量差异可解释
- 用户关系无重复
- 比赛榜单可访问
- 旧 URL 可重定向
- 本地判题闭环不受影响
